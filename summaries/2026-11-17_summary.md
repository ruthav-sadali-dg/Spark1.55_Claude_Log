
## 20261117-001: Arista 720XP-48ZC2 port LED stays dark

**Goal:** Work out why one switch port shows no LED at all, while other empty ports show amber, after a cable was plugged in and an IP was set.

**Guidance given (SOP draft):**
- A dark LED on an empty port can be normal: the port is admin-up with no link. Amber on other empty ports usually means they are disabled (shutdown or errdisabled). Confirm with `show interfaces status`, not with the LEDs.
- The real symptom is no green or link light with the cable plugged in. Check `show interfaces EthernetN status`, `show running-config interfaces EthernetN` (shutdown, forced speed), and `show interfaces EthernetN capabilities` (speeds the port supports versus what the end device supports, e.g. 10/100-only embedded devices).
- The IP normally goes on an SVI (`interface VlanX`), not on the physical port, unless the port is set to `no switchport`.
- Swap the cable, swap the port, and test with a known-good laptop.

**Outcome:** Troubleshooting checklist given. No changes made by Claude.

**Follow-up (show interfaces analysis):** Every `RESERVED-NOT-IN-USE` port is admin down (these are the amber LEDs). Ports that are enabled but have no link stay dark: Et13, 33, 35, 37, 39, 43, 45, 47. **Et17 `FACP_PP20B-9_NAT-10.12.1.93`** (the CLSS/fire panel gateway) logged 334 link status changes in about 2.5 h and had been up only 2 min. The link is flapping, which explains the ARP entry for 10.11.0.93 appearing and then disappearing. Next checks: `show logging | include Ethernet17` (is the timing regular, i.e. reboot-loop or power?), `show mac address-table interface Ethernet17`, swap the cable, check the gateway's dedicated 24 VDC supply and LEDs. Only as a last resort, force speed on both ends. Note: the CLSS manual says NAT is unsupported, and this port is NATed (10.11.0.93 to 10.12.1.93).

**Follow-up (Et13 FIC-UPS-B):** In the pasted output, Et13 is `notconnect`, down 2h20m (the whole uptime since the counters were cleared), with only 3 link changes (the same boot-time count as the shut ports) and 0 packets ever. The switch has never seen link from the UPS. The UPS works with a laptop direct, so its NIC and IP are fine, and an IP doesn't affect link anyway. That makes it physical or speed: the patch path PP20B-7 to Et13, a cable fault, or a 10 Mb-only NIC versus the port's supported speeds. Tests: laptop on Et13 with a known-good patch cord; laptop's link speed when connected direct to the UPS; `show interfaces Ethernet13 capabilities`; `show mac address-table address <UPS MAC>` to see if it landed on another port.
